| 指令 | 不帶參數時 | 位置 |

`docs/HANDOFF.md` 第 189 行寫過的結論在這裡直接適用:

> 記帳系統被放棄的主因是「每天要手動輸入」,所以優化方向是**減少操作次數**,不是增加功能。

## 2. 為什麼不能照抄買菜

買菜點一下就結束,因為只需要**品項**一個資訊。記帳需要**品項 + 金額**兩個。
點「午餐」之後金額從哪來,是整個設計的核心問題。

已排除的兩個方案:

- **按鈕直接含金額**(「午餐 120」一顆按鈕):一下完成,但金額固定。
  今天午餐 95 元就得整句重打,而實際餐費本來就每天不同。
- **點完品項自己打數字**:準確但每筆都要打字,跟現況「記一筆 午餐 120」差別不大,
  沒有真正減少操作。

**採用兩段式**:品項一排、金額一排,兩下完成,跟買菜的操作成本一致。

## 3. 互動流程

```
使用者打「記一筆」                    arg = None
  → 品項按鈕 [午餐][晚餐][早餐][咖啡][飲料][點心]

點「午餐」→ 送出「記一筆 午餐」        arg = "午餐",解析不到金額
  → 金額按鈕 [120][100][150][90][200]
     本文: 不是這些金額的話,直接打「記一筆 午餐 95」

點「120」→ 送出「記一筆 午餐 120」     arg 完整
  → ✅ 已記錄:午餐　-NT$120(餐飲)
```

### 3.1 無狀態是刻意的

**按鈕送出的文字本身攜帶進度**,所以三種狀態純粹靠 `arg` 的內容判斷,
不需要 session、不需要對話狀態機。這與現有架構(每則訊息獨立 parse)完全一致,
也表示使用者自己打完整指令會走同一條路,沒有兩套邏輯要維護。

### 3.2 沒有「其他⋯」按鈕

一顆送出「記一筆 午餐」的「其他」按鈕會回到同一排金額按鈕,形成迴圈。
改成寫在提示本文裡。特殊金額直接打完整指令。

## 4. 程式改動

遵守既有設計原則第 4 條:純邏輯與 I/O 分離。所有新邏輯進 `finance_report.py`,
不碰 Notion 也不碰 LINE。

### 4.1 `finance_report.py`(純邏輯)

| 函式 | 簽章 | 行為 |
|---|---|---|
| `frequent_expense_items` | `(txns, limit=6, pad=True)` | 常記品項,次數多的排前面 |
| `frequent_amounts` | `(txns, item, limit=5, pad=True)` | **該品項**的常用金額 |
| `guess_category` | `(shop)` | 六樣吃的 → `餐飲`;其餘 → `其他` |

**`frequent_expense_items` 只看 `source == "手動"`。**
交易明細裡混著信用卡自動同步的資料,商店名長這樣:
「全聯福利中心－板橋板新」。這種字串放到按鈕上沒有意義,
而且 LINE label 上限 20 字會被截斷成半截店名。

同次數時保持第一次出現的順序 —— 沿用 `kitchen.frequent_items()` 的理由:
每次跳出來的按鈕位置都在動,比排序不準更難用。

`pad=True` 時用預設清單墊到 `limit`。沒歷史就給空按鈕列,
等於這個功能第一天不存在。

**`frequent_amounts` 依品項分別統計。** 午餐學午餐的、咖啡學咖啡的。
共用一份全域金額清單會讓咖啡的按鈕上出現 200 元。

### 4.2 `finance_report.parse_manual()` 改一行

現況第 208 行寫死 `"category": "其他"`。

`notion_db.py:91` 定義了 10 個消費類別(沿用國泰帳單自帶分類),第一個是「餐飲」;
`finance_report.py:78` 的本月支出會按類別算百分比。手動記帳全部落進「其他」,
用得越多那塊佔比越膨脹,分類統計等於作廢。

改成 `guess_category(shop)`。

### 4.3 `command_router.py` — `fin_manual` 三態分流

```
arg 為空          → quick_reply_text(品項提示, [(名稱, f"記一筆 {名稱}") ...])
arg 有品項無金額   → quick_reply_text(金額提示, [(金額, f"記一筆 {品項} {金額}") ...])
arg 完整          → 現有寫入邏輯(不動)
```

第二態目前會回「看不出金額。」+ 用法說明,要改成跳金額按鈕。

`fin_manual` 已在 `_PERSONAL_KINDS`(`command_router.py:447`、`:828`),
不必調整權限。

### 4.5 `notion_db.transactions_load()` 補讀「來源」欄

**這是實作前才發現的前置缺口,不補的話 4.1 的學習邏輯拿不到資料。**

- 交易明細 schema 有「來源」select,選項含「手動」
- `transaction_add()` 有寫入 `_prop_select(txn.get("source"))`
- **但 `transactions_load()` 的 `out.append({...})` 沒有讀回來**

也就是說來源寫得進去、讀不出來。這本身就是個既有缺陷:任何想區分
「自動同步 vs 手動記帳」的功能都做不到,而且不會報錯,只會安靜地
拿到 `None`。

補一行:

```python
"source": _read_select(props, "來源"),
```

## 5. 預設值

### 5.1 預設品項(沒歷史時)

`午餐 / 晚餐 / 早餐 / 咖啡 / 飲料 / 點心`

使用者指定的六樣。用一陣子後會被真實記帳習慣取代。

### 5.2 種子金額(該品項沒歷史時)

| 品項 | 金額 |
|---|---|
| 早餐 | 50 / 60 / 80 |
| 午餐 | 100 / 120 / 150 |
| 晚餐 | 120 / 150 / 200 |
| 咖啡 | 55 / 65 / 85 |
| 飲料 | 35 / 50 / 60 |
| 點心 | 40 / 50 / 80 |

不在表內的品項(使用者自己打出來的,例如「搭車」)沒有種子金額。
第一次記要自己打完整指令,之後就從歷史學得到。

### 5.3 分類判斷

`早餐 / 午餐 / 晚餐 / 咖啡 / 飲料 / 點心 / 宵夜 / 下午茶` → `餐飲`,其餘 → `其他`。

**不新增國泰分類以外的類別。** `notion_db.py:90` 明訂「沿用國泰帳單自帶分類,不自創」。
國泰沒有「交通」,所以「搭車 30」會記成「其他」—— 這是刻意的,
增生分類會讓 Notion 出現兩套命名系統(HANDOFF 4.3 已記錄類別自然增生的問題)。

## 6. 錯誤處理

沿用既有原則(HANDOFF 第 391-396 行):

| 情況 | 行為 |
|---|---|
| Notion 寫入失敗 | 回可讀訊息,不 raise |
| 讀交易歷史失敗 | 退回預設清單,按鈕不消失 |
| 金額解析不出來 | 跳金額按鈕(不再回錯誤字串) |
| 該品項既無歷史也無種子金額 | `frequent_amounts` 回空 list,`quick_reply_text` 不放 `quickReply` key,只留文字提示「直接打『記一筆 搭車 30』」。空的 `quickReply` 物件會被 LINE 當格式錯誤整則退回 |
| 品項名超過 20 字 | `quick_reply_text()` 已內建截短 |
| 按鈕超過 13 顆 | `quick_reply_text()` 已內建截斷 |

## 7. 測試重點

1. **三態分流** — 空 arg / 只有品項 / 品項+金額,各自回對的型別與內容
2. **學習來源隔離** — 餵含信用卡資料的 txns,按鈕不得出現「全聯福利中心－板橋板新」
3. **沒歷史時** — 品項墊到 6 樣、金額不是空陣列
4. **同次數順序穩定** — 相同次數的品項維持第一次出現的順序
5. **分類** — 六樣吃的都判「餐飲」;「搭車」判「其他」
6. **金額依品項** — 午餐的歷史金額不會出現在咖啡的按鈕上
7. **Rich Menu 守門** — 「記一筆」那格 parse 出來不得是 `free_query`
   (照抄 `test_invest_menu.py::test_no_menu_cell_falls_through_to_paid_ai`;
   HANDOFF 4.4 那個「安靜花錢」的坑)
8. **送出的字串可被 parse** — 每顆按鈕的 text 丟回 `parse()` 都要認得
