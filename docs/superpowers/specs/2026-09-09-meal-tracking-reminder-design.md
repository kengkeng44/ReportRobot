## 1. 問題

餐飲是最大的支出類別，但帳上看到的只是刷卡那一部分。

實際資料（2026-08-07 ～ 09-06，31 天，72 筆）：

| 指標 | 數字 |
|---|---:|
| 餐飲支出 | NT$5,032（20.8%，所有類別中最大） |
| 餐飲筆數 | 17 筆 |
| 有餐飲刷卡紀錄的天數 | 13 / 31 |
| 手動記帳筆數 | 6 筆 |
| **有手動記帳的天數** | **4 / 31** |

問題不是使用者不想記，是**沒有東西戳他**。31 天裡有 18 天完全沒有餐飲刷卡紀錄，
那些天吃了什麼、花了多少，帳上是一片空白 —— 而且空白跟「那天沒吃」在報表上
長得一模一樣。

## 2. 五個決定與理由

### 2.1 隔天晚上問，不是當天

國泰「消費彙整通知」每天 14:2x–14:5x 送達，`FINANCE_CRON` 排在台北 15:30 同步
（見 `server.py:53-54`）。當天晚上問的話，當天的刷卡資料還沒進 Notion，系統會
把「已經刷卡但還沒同步」誤判成「沒有紀錄」，然後追問一堆使用者其實刷過的餐。

隔天晚上 21:00 檢查前一天，資料已經齊了。

### 2.2 不足三餐就問缺的，不是「完全沒紀錄才問」

已排除的替選方案是「那天一筆餐飲都沒有才問」。用真實資料模擬，那樣一個月只推
18 次，看起來很安靜 —— 但代價是：8/15 那天只有一筆 688（大概是晚餐），早午餐
可能是現金，系統卻判定「有紀錄」然後閉嘴。

目標是**集齊三餐**，不是「確認那天有花錢」。所以按餐別逐一比對，缺哪一餐問哪一餐。

### 2.3 平日午餐預設自煮，不問也不寫紀錄

週一到週五的午餐由使用者自己煮，固定行為，問了只是噪音。

**不寫一筆 0 元紀錄。** 寫 0 元會污染「餐飲筆數」統計，讓平均值失真。代價是事後
分不出「那天午餐自煮」跟「那天午餐漏記」—— 但因為系統從頭到尾就不問平日午餐，
這兩者本來就不可區分，寫 0 元並沒有換回任何資訊。

分析時平日午餐一律視為 0。

### 2.4 早餐時段的便利商店自動算早餐 —— 但不改類別

使用者早餐**經常在超商解決，而且有刷卡**。實際資料裡全家便利商店－板橋廣榮店
16 筆、均 72 元，跟早餐的價位完全吻合。

如果不自動認定，這些天系統會判定「缺早餐」→ 推播追問 → 使用者手動再記一筆，
**同一筆錢被記兩次**。

規則：**時段 < 10:30 且商店命中便利商店關鍵字 → 餐別 = 早餐**。
午晚餐時段的便利商店不套用（那更可能是飲料、日用品）。

已排除的替選方案是「順便把類別改成餐飲」。那會讓便利商店支出從報表上消失 ——
而那 1,538 元／月正好是最該檢討的一塊。

**類別和餐別是兩個維度：**

| 欄位 | 回答的問題 | 早餐超商那筆 |
|---|---|---|
| 類別 | 在哪裡買 | 超市∕量販 |
| 餐別 | 這是哪一餐 | 早餐 |

三餐花費統計走「餐別」欄位，不走「類別」。

### 2.5 沿用對話式輸入，一句話講完

按 ➕ → 回「請說。」→ 使用者一句話講完缺的餐 → AI 解析 → 寫入。

跟待辦升級同一套 `_PENDING` 模式（`personal.py`），使用者只要學一次互動方式。

## 3. 資料層

### 3.1 交易明細新增兩欄

在 `notion_db.py` 的 `"交易明細"` schema 加：

```python
# 國泰 parser 一直有解析授權時間（parsers/cathay_daily.py:136），
# 但 transaction_add 沒有這個欄位，值在寫入時就蒸發了。
# 有時間才分得出 12:30 那筆是午餐、19:40 那筆是晚餐。
"時間": {"rich_text": {}},                       # HH:MM，24 小時制
# 類別回答「在哪買」，餐別回答「這是哪一餐」—— 兩個維度不互相取代。
"餐別": _select(("早餐", "yellow"), ("午餐", "orange"), ("晚餐", "blue")),
```

`_ensure_properties` 只補缺欄、不動既有資料，所以現存的 72 筆會安全地拿到兩個空欄位。

### 3.2 既有資料補不回時間

Fingerprint **刻意不含時間**（`parsers/cathay_daily.py:39`：同日同店同金額視為同一筆，
這樣重跑排程不會產生重複）。因此重跑同步會被去重擋掉，時間欄位只對加上去之後的
資料生效。

這是可接受的：三餐追蹤的價值在未來的資料，不在回填歷史。

### 3.3 寫入路徑要接上

- `parsers/cathay_daily.py` → 已經有 `"time"`，不用改
- `finance_sync.py` → 把 `time` 往下傳給 `transaction_add`
- `notion_db.transaction_add()` → 新增 `"時間"` 與 `"餐別"` 兩個 candidate 欄位，
  照既有慣例：**沒帶就不寫**（`_prop_select(txn.get("meal"))` 為 None 時整個 key 被濾掉）
- `notion_db.transactions_load()` → 讀回 `"time"` 與 `"meal"`

## 4. 餐別推斷

新模組 `meal_track.py`。純邏輯，不碰網路，全部可單元測試。

### 4.1 時段對照

```python
# 界線刻意留白：14:30–16:30 之間的消費不算任何一餐（下午茶），
# 22:00 之後也不算（宵夜）。硬塞進三餐會讓「這天晚餐花 1,200」
# 這種數字失去意義。
BREAKFAST_END = time(10, 30)
LUNCH_START, LUNCH_END = time(10, 30), time(14, 30)
DINNER_START, DINNER_END = time(16, 30), time(22, 0)
```

### 4.2 `infer_meal(category, shop, hhmm) -> str | None`

| 條件 | 結果 |
|---|---|
| 時間空白或格式不對 | `None` |
| 類別 = 餐飲，時段命中 | 對應餐別 |
| 類別 = 餐飲，時段沒命中（下午茶／宵夜） | `None` |
| 商店命中便利商店，時段 < 10:30 | `早餐` |
| 商店命中便利商店，其他時段 | `None` |
| 其他 | `None` |

便利商店關鍵字沿用子字串比對，跟 `finance_report._SHARED_SHOPS` 同一個風格：

```python
# 用子字串比對而非完全相等：國泰給的店名是「全家便利商店－板橋廣榮店」，
# 分店會變但「全家」不會。
_CVS_KEYWORDS = ("全家", "統一超商", "萊爾富", "ＯＫ超商")
```

### 4.3 `meals_needed(day) -> tuple`

```python
# 平日午餐由使用者自己煮 —— 固定行為，問了只是噪音。
if day.weekday() < 5:          # 週一(0) ~ 週五(4)
    return ("早餐", "晚餐")
return ("早餐", "午餐", "晚餐")
```

### 4.4 `missing_meals(day, rows) -> tuple`

`rows` 是那一天的交易明細。回傳 `meals_needed(day)` 扣掉已經有紀錄的餐別後剩下的。
全都有 → 回空 tuple → 不推播。

## 5. 排程

`server.py` 新增一個 job：

```python
# UTC 13:00 = 台北 21:00。晚上問前一天：國泰 15:30 才同步，
# 當天晚上問會把「還沒同步」誤判成「沒紀錄」。
MEAL_CRON = _cron_or_default("MEAL_CRON", "0 13 * * *")
```

沿用既有的 `_cron_or_default`（env 打錯不該讓 startup crash）與
`_scheduler_error_listener`（job 失敗會通知 admin）。

### 5.1 配額

LINE 免費方案每月 200 則 push。以真實資料模擬，這條規則一個月約推 28 次；
加上既有推播（本月推估 53 則）合計約 81 / 200 = **41%**，不會觸發 80% 警示。

`line_quota.bump()` 照既有慣例呼叫。

## 6. 推播與對話流程

### 6.1 推播內容

```
🍽 昨天（9/08 週一）還缺：早餐、晚餐
   午餐已預設自煮
   [ ➕ 補記 ]  [ 都沒花 ]
```

平日不列午餐；假日三餐都列。

早餐已被便利商店規則認定的話，「早餐」不會出現在缺的清單裡，也不會有提示行 ——
那筆錢已經在帳上了，再提一次只會誘發重複記帳。

### 6.2 對話狀態

沿用 `personal.py` 的 `_PENDING_TODO` 模式，新增 `_PENDING_MEAL`：

```python
# {user_id: {"date": "2026-09-08", "meals": ("早餐", "晚餐")}}
_PENDING_MEAL = {}
```

跟待辦一樣的逃生規則：**任何已知指令都取消待命**。Rich Menu 的按鈕送的是純文字，
而且不是每一顆都帶斜線（`setup_richmenu.py:76` 的「記一筆」就是裸的），所以
判斷條件是「命中已知指令」而不是「開頭是 `/`」。

### 6.3 流程

```
按 ➕ 補記
  → 存 _PENDING_MEAL[user_id]
  → 回「請說。缺：早餐、晚餐」

使用者：早餐 60 晚餐 200
  → AI 解析 → {"早餐": 60, "晚餐": 200}
  → 逐餐呼叫 transaction_add(來源="手動", 類別="餐飲", 餐別=X, 日期=D-1)
  → 回「✅ 已記錄 9/08：早餐 60、晚餐 200」

按「都沒花」
  → 清掉 pending，回「好，9/08 不記錄。」
  → 不寫任何紀錄（見 2.3 的理由）
```

不需要「已處理」標記：每天只問前一天，隔天問的是不同的日期，不會重複追問同一天。

### 6.4 分帳

沿用現有語法：「晚餐 400 共同」→ `原始總額 = 400`、`金額 = 200`、`分攤類型 = 共同`，
跟 `finance_report.MY_SHARE` 同一個常數。沒講就是個人。

## 7. AI 解析

`prompts.py` 新增 `MEAL_PARSE_PROMPT`，走 `phrasebook.py` 的 `_ai` seam 模式 ——
測試整段替換那個函式，零 SDK mock。

**輸入：** 使用者那句話 + 缺的餐別清單
**輸出：** JSON，只含有講到的餐

```json
{"早餐": 60, "晚餐": 200}
```

**防呆：**

| 情況 | 行為 |
|---|---|
| 解析不出任何餐 | 回快速回覆按鈕請他重講，不寫入 |
| 講了沒被問的餐（平日講午餐） | 照樣記錄 —— 使用者比規則清楚自己那天有沒有出去吃 |
| 金額不是正整數 | 那一餐跳過，其他照記，回覆說明哪一餐沒收到 |
| AI 回傳不是合法 JSON | 當作解析失敗，走重講流程 |

**絕不猜金額。** 記錯數字比沒記更糟：沒記的空白看得出來，記錯的數字看不出來。

## 9. 不做的事

- **不回填歷史資料的時間與餐別。** Fingerprint 不含時間，重跑會被去重擋掉；
  另寫回填腳本的成本遠高於它的價值。
- **不做每餐即時推播。** 一天三則 push × 30 天 = 90 則，配額會到七成。
- **不自動把便利商店改成餐飲類別。** 見 2.4。
- **不做「本週三餐花費」報表。** 資料要先累積夠才有意義，等跑滿一個月再說。
