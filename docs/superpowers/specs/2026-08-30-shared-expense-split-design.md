# 共同消費分攤 + 記帳按鈕統計調整 — 設計

**日期:** 2026-08-30
**狀態:** 設計已確認,尚未實作
**前置:** `docs/superpowers/specs/2026-08-19-manual-entry-quick-reply-design.md`(兩段式 Quick Reply)

---

## 1. 問題

手動記帳目前把每一筆都當成「這筆錢全是我出的」。實際上有一部分是兩個人分攤的
共同消費 —— 那些筆的金額直接進「本月支出」會**高估使用者的真實負擔**,而且
帳面上分不出哪些是共同的。

同時,金額 Quick Reply 的統計沒有時間窗:`frequent_amounts()` 吃全部歷史,
記錄一多之後,兩年前的價位會永遠卡在按鈕上,物價漲了按鈕不會跟上。

## 2. 三個決定與理由

### 2.1 一半一半,不做權重

原始需求是「共同消費我佔 1.2 份,因為我吃比較多」。確認後改為**均分**,
理由是煮飯由使用者負責,勞務抵掉了食量差。

程式裡仍寫成常數而非散落的 `/ 2`:

```python
MY_SHARE = 0.5   # 共同消費裡我負擔的比例。改這一個數字就能調整分攤。
```

不是為了「未來擴充」——是為了讓「這個 0.5 是一個政策決定」在程式碼裡看得見。
散落的 `/ 2` 讀起來像數學,常數讀起來像規則。

### 2.2 「金額」欄存分攤額,不存總額

| 欄位 | 個人消費 | 共同消費 |
|---|---|---|
| 金額(既有) | 600 | **300** |
| 原始總額(新增) | 600 | 600 |
| 分攤類型(新增) | 個人 | 共同 |

**「金額」欄的語意維持不變:使用者實際負擔多少。**

已排除的替選方案是「金額存總額、另存分攤額」。那樣所有下游都要改成讀新欄位:
`format_monthly_spending`、`format_recent`、`format_latest_day_spending`、
`format_card_bills`、`digest.py` 的每日個人信、`build_dashboard.py`。
漏改任何一處,支出就被高估 —— 而且不會報錯,畫面上只是數字變大,
看起來像那個月花得比較兇。

代價是帳面上看不到整桌多少錢,所以才有「原始總額」欄補回這個資訊。

### 2.3 即時重算 + 時間窗,不做月更快取

原始需求是「一個月一次自動更新常花金額」。現況是 `frequent_amounts()`
**每次按都即時從 Notion 重算**,已經比月更即時。改成月更是退步:
月中養成的新習慣要等到下個月才會反映在按鈕上。

省下的那次 Notion 查詢也不值得 —— 上一段跳品項按鈕時本來就查過一次了。

真正該修的是統計方式(見 4.2)。

## 3. 互動流程

「個人 / 共同」插在**最後一段**(使用者選定)。維持既有的**無狀態**設計:
按鈕送出的文字自己攜帶進度,不存 session,Railway redeploy 不會記錯帳。

```
使用者打：記一筆
  ↓  [午餐] [晚餐] [咖啡] [飲料] …            ← 常記品項
使用者點：晚餐          (送出「記一筆 晚餐」)
  ↓  [600] [150] [500] [200] …                ← 常花金額
使用者點：600           (送出「記一筆 晚餐 600」)
  ↓  [個人] [共同]                            ← 新增這一段
使用者點：共同          (送出「記一筆 晚餐 600 共同」)
  ↓
✅ 已記錄：晚餐　共同 NT$600
   你分攤 NT$300（餐飲）
```

四種狀態靠 `arg` 內容判斷,與既有三態設計一致:

| `arg` | 狀態 | 回應 |
|---|---|---|
| 空 | 還不知道品項 | 常記品項按鈕 |
| `晚餐` | 有品項、沒金額 | 常花金額按鈕 |
| `晚餐 600` | 有金額、沒分攤類型 | 個人 / 共同按鈕 |
| `晚餐 600 共同` | 齊全 | 寫入 Notion |

**打字路徑保留一步到位:** 直接打完整的 `記一筆 晚餐 600 共同` 不會多問。
只打 `記一筆 晚餐 600` 才跳第三段。

### 3.1 已知的取捨:金額按鈕會混型態

選「最後一段」的必然結果 —— 跳金額按鈕的當下還不知道這筆是個人還是共同,
所以個人的午餐 120 和共同的晚餐 600 會出現在同一排。

緩解方式見 4.3(按品項推斷慣用型態),不改變使用者選定的順序。

## 4. 資料與演算法

### 4.1 Notion schema

`notion_db._SCHEMAS["交易明細"]` 新增兩欄:

```python
"分攤類型": _select(("個人", "default"), ("共同", "blue")),
"原始總額": {"number": {"format": "number"}},
```

`_ensure_properties()` 只補不刪,線上既有 DB 會自動長出這兩欄,既有資料列不動。

**舊資料的讀取規則**(`transactions_load`):

- `分攤類型` 讀不到 → `"個人"`。既有的國泰同步資料本來就是使用者自己刷的
- `原始總額` 讀不到 → 回退成 `金額` 的值。個人消費兩者本來就相等

這兩條 fallback 讓所有既有統計不必特判 `None`。

### 4.2 分攤計算

```python
MY_SHARE = 0.5

def my_share_of(total):
    """共同消費裡我負擔多少。四捨五入到整數 —— 台幣沒有小數。"""
    return int(total * MY_SHARE + 0.5)
```

**不用內建 `round()`**:Python 的 `round()` 是 banker's rounding,
`round(302.5)` 得到 302 而 `round(303.5)` 得到 304 —— 同樣是 .5 卻一個往下
一個往上。記帳上這種不一致查起來會懷疑人生。`int(x + 0.5)` 一律往上,
可預測。(金額為正,不必處理負數情形。)

### 4.3 Quick Reply 統計調整

三個改動,`frequent_expense_items()` 與 `frequent_amounts()` 都套用:

**(a) 90 天時間窗** — 超過 90 天的記錄不計入。

**(b) 時間加權** — 近期的記錄算比較多次:

| 距今 | 權重 |
|---|---|
| 0–30 天 | ×3 |
| 31–60 天 | ×2 |
| 61–90 天 | ×1 |
| 90 天以上 | 不計 |

原本的「同次數保持第一次出現順序」規則保留 —— 按鈕位置每次都在動,
比排序不準更難用。

兩個函式都新增 `today=None` 參數(預設 `date.today()`),讓測試能注入固定日期。
沒有這個參數,測試就得依賴系統時鐘,跑起來時好時壞。

**(c) 金額統計用「原始總額」,並按品項推斷慣用型態**

金額按鈕上的數字是**使用者要打進去的錢**(整桌 600),不是分攤額(300)。
用金額欄統計的話,共同消費的按鈕會每次砍半,愈跳愈小。

`frequent_amounts(txns, item, today=None)` 的流程:

1. 篩出該品項、90 天內、`source == "手動"` 的記錄
2. 依 `分攤類型` 分兩組,各自算加權次數
3. 取加權次數較高的那組當「慣用型態」,只用該組記錄算金額
4. 該組筆數 < 2 時,退回用全部記錄 —— 樣本太少的推斷不可信,
   而且會讓按鈕少到不夠用
5. 統計對象是 `原始總額`

種子金額 `_SEED_AMOUNTS` 與 `pad` 補位機制維持不變。

### 4.4 Fingerprint

個人消費維持既有格式,避免動到既有資料的比對基準:

```
個人：手動|{day}|{amount}|{shop}
共同：手動|{day}|{total}|{shop}|共同
```

共同消費加後綴,是為了讓「個人 300」與「共同 600(分攤 300)」不撞號 ——
兩者的「金額」欄都是 300,不加區別就會產生相同 fingerprint。

### 4.5 解析

`parse_manual()` 先從尾端剝離 `個人` / `共同` 關鍵字,再走既有的金額/品項解析。
不剝的話 `記一筆 晚餐 600 共同` 會被解析成商店名「晚餐 共同」。

回傳的 dict 新增兩個鍵:`split_type`、`total`(原始總額)。
`amount` 維持「我實際負擔」的語意。

**`split_type` 的三態約定**,呼叫端靠它決定下一步:

| 輸入 | 回傳 | 呼叫端動作 |
|---|---|---|
| 沒有金額 | `None`(整個 dict) | 跳金額按鈕 |
| `晚餐 600` | dict,`split_type=None` | 跳個人 / 共同按鈕 |
| `晚餐 600 共同` | dict,`split_type="共同"` | 寫入 Notion |

`split_type=None` 時 `amount` 先等於 `total`,但呼叫端不該用它 —— 那是還沒
決定分攤前的暫定值。整個 dict 只用來判斷「金額解析成功了」。

## 5. 報表

`format_monthly_spending()` 在總額下方加一行,只在當月有共同消費時出現:

```
本月支出 NT$18,420
　其中共同分攤 NT$6,200（原始 NT$12,400）
```

沒有共同消費的月份不印這行 —— 常態是零的欄位每個月都佔一行,會讓人不再讀它。

其餘報表(`format_recent`、`format_latest_day_spending`、每日個人信、
dashboard)因為讀的是「金額」欄,語意未變,**不需修改**。

## 6. 錯誤處理

沿用專案既有原則:Notion 失敗一律 fallback、不 raise,記帳寫入失敗不能拖垮
每日推播。

新增段落的具體行為:

- **個人 / 共同按鈕不依賴 Notion** —— 兩顆靜態按鈕,Notion 掛掉照樣跳得出來,
  使用者仍能完成到「按下共同」這一步
- 真正寫入時 Notion 掛掉,維持既有訊息「寫入 Notion 失敗,請稍後再試。」
- 統計函式讀不到資料時,`pad` 機制讓按鈕退回種子金額,不會給出空的 quickReply
  (空 quickReply 會被 LINE 當格式錯誤,整則訊息退回)

| 對象 | 測什麼 |
|---|---|
| `my_share_of` | 偶數整除、奇數進位(605 → 303)、.5 邊界一律往上 |
| `parse_manual` | 三段完整輸入、尾端關鍵字剝離、缺分攤類型回 `None` 型態、既有兩段輸入不回歸 |
| fingerprint | 個人格式未變、個人 300 與共同 600 不撞號 |
| `frequent_amounts` | 90 天窗排除舊資料、加權排序、用原始總額而非分攤額、慣用型態推斷、樣本 < 2 退回全部 |
| `frequent_expense_items` | 90 天窗、加權排序、pad 行為不變 |
| `transactions_load` | 舊資料缺兩欄時的 fallback(`個人` / 回退金額) |
| `command_router` 四態 | 空 / 品項 / 品項+金額 / 全齊,各自的回應型態 |

### 7.1 一個既有行為**會**改變(刻意的)

`記一筆 午餐 120` 原本直接寫入,現在會跳出個人 / 共同按鈕。這是把分攤問題
放在最後一段的必然結果,不是回歸。

牽動的既有測試需要更新斷言,更新時要能明確講出「這是設計變更」而不是把測試
改成順著實作走。其餘既有手動記帳測試必須全綠。

想維持一步到位的打字習慣,完整輸入 `記一筆 午餐 120 個人` 即可。

### 7.2 說明文字要一起改

`command_router.py` 的 `HELP_TEXT`(約 121-123 行)、`_MANUAL_USAGE`、
`_MANUAL_QUICK_HINT` 都寫著舊的兩段式用法,必須同步更新,否則 `/help` 會教
使用者一個已經不成立的流程。

## 8. 不做什麼

- **不做 1.2 權重**:已改為均分(2.1)
- **不做月更快取表**:即時重算已更好(2.3)
- **不做「共同消費」的對方欠款追蹤**:這是記帳,不是對帳系統。
  誰欠誰多少要靠另一套流程,不在這次範圍
- **不改既有報表的讀取欄位**:金額欄語意未變是這個設計的核心價值(2.2)
- **不動國泰同步路徑**:自動同步的資料一律個人,不經過分攤邏輯
