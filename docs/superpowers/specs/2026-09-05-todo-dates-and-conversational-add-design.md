# 待辦升級：起訖日期、優先度、對話式新增 — 設計

**日期：** 2026-09-05
**狀態：** 已與使用者確認，待寫實作計畫

---

## 1. 問題

現在的待辦有三個毛病：

1. **每日信那張卡標題是「📋 今日待辦」，內容卻是全部未完成待辦。**
   `personal.format_todos()` 回的是 `list_todos()` 的全部，沒有任何日期概念——
   因為 Notion 的 `Todos` 表根本沒有日期欄位。「今日」兩個字目前是假的。

2. **待辦沒有時間概念。** 使用者要知道「這件事是幾月幾號到幾月幾號」。

3. **新增待辦要打指令。** 現在只能打 `/待辦 加 [內容]`。使用者在手機上，
   想要「按一顆按鈕 → 機器人說『請說』 → 直接講話 → 記進去」。

另外使用者要求日期能用**語意**講：「下禮拜一」要自動換算成實際日期。

---

## 2. 決策與理由

### 2.1 Notion `Todos` 加兩個欄位

| 欄位 | 型別 | 說明 |
|---|---|---|
| `期間` | `date` | Notion 原生日期**區間**（`start` + `end`）。只給一天就 `end` 留空 |
| `優先度` | `select` | `P0` / `P1` / `P2` / `P3` |

**為什麼用一個日期區間而不是「開始日」「結束日」兩欄：**
Notion 的 date property 原生支援區間，頁面上顯示成 `9月1日 → 9月10日`，
排序與篩選都吃同一個型別。拆成兩欄要自己維護「結束不能早於開始」，
而 Notion 的日期選擇器本來就擋掉了。

**「截止日」的定義：** `end` 有值就用 `end`，沒有就用 `start`。
單日待辦（只講「明天交」）不需要被迫填兩個日期。

兩個欄位由既有的 `notion_db._ensure_properties` 自動補上。
**那個函式只加不刪**，現有待辦資料一筆都不會動到。

### 2.2 每日信的篩選規則

```
截止日 ≤ 今天   OR   優先度 = P0
```

排序：**逾期的最前面**（標 `⚠️ 逾期 N 天`）→ 今天到期 → P0 且無截止日。

「截止日」與「P0」是兩個獨立的維度，刻意不合併：
截止日回答「什麼時候該做」，P0 回答「不管什麼時候都得盯著」。
只用日期篩，沒設日期的重要事情會消失；只用優先度篩，時效性就沒了。

**已知後果（使用者已知情並接受）：**
現有待辦兩欄都是空的，所以這個功能上線後每日信的待辦卡會是空的，
直到使用者補上日期或標 P0。LINE 打「待辦」照樣看得到全部——
跟 2026-09-04 拿掉冰箱提醒是同一個原則：**記錄還在，通知變安靜。**

### 2.3 對話式新增：一句話說完，AI 拆解

```
你: [按 Rich Menu「待辦」]        → /待辦 → 待辦清單卡片（底下多一顆「➕ 加一件事」）
你: [按 ➕]                       → postback
我: 請說。
你: P0 下禮拜交社宅資料
我: ✅ 已記下：交社宅資料
    📅 9/08（一）　🔴 P0
```

一句話同時帶內容、日期、優先度，AI/規則負責拆。
分段問（內容 → 時間 → 優先度）被否決：來回三四輪才記得成一件事，
跟使用者要的「不用打指令就直接記入」相反。

### 2.4 防呆：先記下來，再跳按鈕補

漏講日期或優先度時：

```
你: 交社宅資料
我: ✅ 已記下：交社宅資料
    ⚠️ 還沒設截止日
    [今天] [明天] [本週五] [下週一] [不設]
```

**內容先寫進 Notion，才問缺的欄位。** 順序是刻意的：
使用者中途跑掉、或 LINE 連線斷了，至少那件事已經記住了。
先問再存的話，中斷等於整件事沒記到——那正是待辦最不能發生的事。

補值走 postback 更新既有的 page，不是新增第二筆。

兩個都缺時**只問截止日**，優先度留空（顯示時視為 P2）。
連問兩輪按鈕會讓「按一下就好」變成「按三下」。
優先度可以事後在 Notion 上改，截止日不補則會從信裡消失——後果不對等。

### 2.5 待命狀態：記憶體，被任何已知指令解除

`personal.py` 開一個 `_PENDING_TODO`（`user_id → {"started_at": datetime}`），
跟既有的 `_TODOS` cache 同一套做法（模組層 dict + `_LOCK`）。

**不進 Notion**：這個狀態的壽命是幾秒，為它多一次 API 往返不划算。
Railway 重啟丟掉的代價只是使用者要重按一次 ➕。

**逾時 10 分鐘**自動失效。沒有逾時的話，一個忘掉的待命狀態會把使用者
隔天隨口講的任何一句話變成待辦。

**解除規則（使用者確認過）：**

> 待命中收到的訊息，只要 `command_router.parse()` 認得出是已知指令，
> 就解除待命、回一句「已取消新增待辦」，然後照常執行那個指令。
> 認不出來的才當作待辦內容。

**為什麼不是「以 `/` 開頭就解除」：**
Rich Menu 的按鈕送的是**文字訊息**，而且不是每顆都有斜線——
`setup_richmenu.py:76` 的「記一筆」送的是裸的 `記一筆`。
只認斜線的話，使用者按「記一筆」會得到一筆叫「記一筆」的待辦。

**注意主選單的「財務」不會解除待命**，因為它是 `("switch", "finance")` ——
那是 LINE channel 層的選單換頁，**根本不會送 webhook 給伺服器**。
真正解除的是使用者接著按的那一顆（本月支出 / 記一筆 / …）。
從使用者角度看沒有差別：翻頁再按功能，就取消了。

**已知限制：** 沒辦法新增一筆內容剛好叫「記一筆」「待辦」「快過期」的待辦。
改寫成「記一筆帳」即可。這個代價比「按按鈕逃不掉」小得多。

### 2.6 日期解析：規則優先，AI 補位

新模組 `todo_parse.py`，純邏輯 + 一個 `_ai` 接縫（跟 `phrasebook.py` 同一套手法，
測試整個換掉 `_ai`，不用 mock SDK）。

**規則吃掉這些**（不呼叫 AI，即時、免費、可測）：

| 說法 | 結果（以 2026-09-05 週五為基準）|
|---|---|
| 今天 | 9/05 |
| 明天 | 9/06 |
| 後天 | 9/07 |
| 大後天 | 9/08 |
| 這週一 / 本週一 | 9/01（**本週已過的日子也算本週**）|
| 下週一 / 下禮拜一 | 9/08 |
| 週五 / 禮拜五（沒講這週下週）| 9/05，**今天就是週五時取今天** |
| 三天後 | 9/08 |
| 一週後 | 9/12 |
| 9/15、9月15日、915（三位以上數字不視為日期）| 9/15 |
| 9/1-9/10、9/1到9/10 | 區間 |

**「下週X」的算法要釘死：** 以今天為基準找**本週一**（`today - today.weekday()`），
加 7 天得下週一，再加 `X-1` 天。跨月跨年由 `date` 型別自己處理。
這是最容易寫錯的地方，每個 case 都要有測試。

**AI 只在規則認不出來時呼叫**（「中秋前」「月底前」「下下週」「農曆年前」）。

**AI 失敗時**：照樣把內容記進 Notion，跳防呆按鈕讓使用者選。
不因為解析日期失敗就整件事不記——那違反 2.4 的原則。

### 2.7 優先度解析

規則即可，不需要 AI：句子裡出現 `P0`/`P1`/`P2`/`P3`（大小寫皆可）就取用，
並從待辦內容裡移除那個 token。沒出現就留空。

「很急」「重要」這類自然語言**不解析成優先度**：
那是主觀詞，猜錯會讓使用者對整個功能失去信任，而防呆按鈕點一下就解決了。

## 3. 模組設計

| 檔案 | 動作 | 職責 |
|---|---|---|
| `todo_parse.py` | **新增** | 純邏輯：一句話 → `{text, start, end, priority}`。規則 + `_ai` 接縫 |
| `notion_db.py` | 改 | `_SCHEMAS["Todos"]` 加兩欄；`todos_create` 收日期與優先度；新增 `todos_update_fields` |
| `personal.py` | 改 | `add_todo` 收日期與優先度；新增 `_PENDING_TODO` 待命狀態；新增 `todos_due_today()` 與 `format_today_todos()` |
| `command_router.py` | 改 | 待命狀態攔截（在 `handle` 最前面）；`➕` 與防呆按鈕的 postback |
| `flex_builder.py` | 改 | `todo_list_flex` 底部加「➕ 加一件事」；每列顯示日期與優先度 |
| `daily_report.py` | 改 | 待辦區塊改用 `personal.format_today_todos()` |
| `prompts.py` | 改 | 加 `TODO_DATE_PROMPT`（AI 補位用）|

**為什麼 `todo_parse.py` 獨立成檔而不是塞進 `personal.py`：**
`personal.py` 已經同時管待辦與提醒兩套東西。日期解析是一組
純函式、零 I/O、規則密集、測試量大的邏輯，混進去會讓那個檔更難讀。

**`format_todos` 完全不動。** LINE 打「待辦」的行為維持原樣，
只加新函式給每日信用——動它會弄壞指令查詢，而那個壞法在信上看不出來。

## 4. 錯誤處理

| 情況 | 行為 |
|---|---|
| AI 呼叫失敗 / 逾時 | 記下內容，跳防呆按鈕。**不中斷** |
| AI 回了無法解析的日期 | 同上，當作沒解析到 |
| Notion 寫入失敗 | 沿用 `add_todo` 既有做法：記憶體照記，印錯誤，回覆照給 |
| 待命中 Railway 重啟 | 待命狀態消失，使用者下一句話當一般訊息處理（不會誤記）|
| 待命逾時（10 分鐘）| 同上 |
| 使用者按 ➕ 兩次 | 覆蓋既有待命狀態，重新計時，不報錯 |

## 5. 測試

`todo_parse.py` 是純邏輯，**零 mock**：所有規則案例直接餵字串斷言結果。
基準日期一律用固定的 `date(2026, 9, 5)`（週五），不用 `today()`——
會隨時間漂移的測試等於沒有測試。

必測的邊界：

- 跨月：9/29 說「下週一」→ 10/06
- 跨年：12/29 說「下週三」→ 隔年 1/07
- 「這週一」在週五講 → 本週一（已經過去的日子）
- 「週五」在週五講 → 今天
- 篩選規則：逾期 / 今天到期 / P0 無日期 / 非 P0 無日期（不顯示）
- 待命狀態：已知指令解除、未知文字當內容、逾時、重複按 ➕

`command_router` 的待命攔截要驗**它排在所有指令解析之前**，
否則「待辦」這種字會先被指令吃掉。

## 6. 刻意不做（YAGNI）

| 不做 | 理由 |
|---|---|
| 重複待辦（每週一交報告）| 使用者沒提；會把 schema 與篩選邏輯撐複雜一個量級 |
| 待辦到期推播提醒 | 已經有 `Reminders` 那一套，兩個系統混在一起會互相干擾 |
| 改 Rich Menu 加「加待辦」格 | 要重產選單圖 + 重跑 `setup-richmenu`，而清單卡片上那顆 ➕ 已經夠用 |
| 自然語言優先度（「很急」）| 主觀詞猜錯會毀掉信任，按鈕點一下就解決 |
| 待辦編輯（改內容 / 改日期）| 去 Notion 改。做成 LINE 對話流程要一整套狀態機 |

---

## 7. 已排除的方案

| 方案 | 為什麼不採用 |
|---|---|
| 信裡顯示「今天落在起訖區間內」的待辦 | 使用者選了「截止日 ≤ 今天」——一件事做十天，不需要在信裡出現十次 |
| 沒日期的待辦一律顯示 | 會讓信回到「全部列出來」，跟使用者要的安靜相反 |
| 新增時沒講日期就預設今天 | 隨手記的事會變成隔天就逾期，信裡一直紅字 |
| 分段問（內容 → 時間 → 優先度）| 三四輪才記成一件事，跟「直接記入」相反 |
| 全部丟給 AI 解析日期 | 每加一筆就一次 API 呼叫（1-2 秒），AI 掛掉就完全設不了日期 |
| 全部用規則、不接 AI | 「中秋前」這種要使用者自己換算 |
| 待命狀態存 Notion | 壽命只有幾秒，多一次 API 往返不划算 |
| 「以 `/` 開頭就解除待命」| Rich Menu 的「記一筆」送裸指令，沒有斜線，會被誤記成待辦 |

---

## 8. 使用者要手動做的事

1. **部署後不用建表**——`_ensure_properties` 開機時自動補上 `期間` 與 `優先度` 兩欄。
2. **現有待辦要補資料**才會回到每日信裡：去 Notion 補截止日，或標 P0。
   不補的話它們仍然在，LINE 打「待辦」看得到，只是不進信。
